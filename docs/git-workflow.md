# Git workflow

Читать перед созданием ветки, коммита или PR.

GitHub Flow, соло-проект. `main` — продакшен: каждый merge деплоится на GitHub Pages через Actions.

## Ветки

- Прямые коммиты и push в `main` запрещены, даже для опечаток. Защита ветки действует и на админа; не пытаться её обходить.
- Короткоживущие ветки от `main`: `feat/`, `fix/`, `content/`, `chore/`, `docs/` + slug в kebab-case.
- Никаких `develop` и `release`. Теги только для вех.

## Pull request

- PR на каждое изменение. Merge только когда зелёная обязательная проверка `check` (workflow `CI`). Апрувы не нужны.
- Сразу после `gh pr create` включить auto-merge: `gh pr merge <number> --auto --squash` (владелец разрешил это для каждого PR). GitHub сам смержит, когда пройдёт `check`: не ждать и не мержить вручную. Если CI упал, чинить в той же ветке, auto-merge останется взведённым. Не включать auto-merge на PR из форков и на чужие PR.
- Только squash merge (merge-коммиты и rebase отключены). Заголовок PR становится заголовком коммита, тело — телом коммита, поэтому писать оба сразу как финальные. Смерженные ветки удаляются автоматически.
- Заголовки PR — Conventional Commits (`feat:`, `fix:`, `content:`, `chore:`, `docs:`, `test:`) на русском. Тело короткое: что и зачем.
- Крупные изменения контента (массовые правки вопросов) — отдельными PR по категориям, а не одним огромным.

## После merge

Синхронизировать локальный `main`: `git switch main && git pull --ff-only`. Если `--ff-only` не проходит, локальный `main` разошёлся: остановиться и сообщить владельцу.

## Репозиторий публичный

Не коммитить секреты, локальные пути, id страниц Notion и сырые выгрузки.
