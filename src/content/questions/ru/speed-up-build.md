---
title: "Какие советы для ускорения сборки проекта вы знаете?"
category: tooling
order: 45
---

**Сначала измерить, а не гадать.** `Product → Perform Action → Build with Timing Summary` собирает проект один раз и в конце показывает, сколько времени ушло на каждую категорию (компиляция, линковка, скрипты) — без этого непонятно, что на самом деле тормозит сборку. Компилятору можно также включить диагностику самых медленных функций и выражений типов (`-Xfrontend -warn-long-function-bodies=200`, `-Xfrontend -warn-long-expression-type-checking=200`).

Дальше — по частым причинам:

- **Не гонять лишние скрипты на каждой сборке.** Run Script фазы (SwiftLint, генерация кода и т. п.) можно ограничить нужной конфигурацией через «Based on dependency analysis» и `Input/Output Files`, чтобы Xcode пропускал скрипт, если ничего не изменилось, либо через проверку `${CONFIGURATION}` внутри скрипта — например, запускать SwiftLint только для Debug-сборок.
- **Модуляризация.** Разбиение проекта на независимые модули (Swift Package'и или отдельные таргеты) позволяет Xcode кэшировать и пересобирать только изменившиеся модули, а не весь проект целиком, и собирать независимые модули параллельно.
- **Инкрементальная сборка.** Компилятор пересобирает только изменённые файлы и их зависимости — этому помогает избегать «жирных» файлов с большим количеством не связанных друг с другом типов и разрывать циклические зависимости между модулями.
- **Whole Module Optimization** (`SWIFT_WHOLE_MODULE_OPTIMIZATION`, часть `-O`) — компилятор оптимизирует и распараллеливает компиляцию всех файлов модуля разом; уместно для Release, но не всегда ускоряет инкрементальные Debug-сборки, где важнее скорость единичного цикла правка → сборка.
- **Явная типизация в горячих местах.** Сложный вывод типов (длинные цепочки `map`/`filter`/`reduce`, операторы с перегрузками, большие literal-выражения) заметно увеличивает время тайпчекинга — помогает разбить выражение на шаги или явно указать тип.
- **Параллельная сборка и число исполнителей.** Xcode по умолчанию собирает файлы параллельно; для CI стоит убедиться, что используется достаточное число ядер и включён `-parallelizeTargets` у `xcodebuild`.
- **Зависимости.** Меньше тяжёлых сторонних библиотек и статических линковок, где это оправдано, — динамическая линковка не требует пересборки при каждом изменении зависимого кода; там, где обновления библиотек редки, наоборот выигрывает статическая линковка за счёт более быстрого запуска, но не сборки.
- **Кеш сборки и CI.** Использовать `Derived Data` и не чистить его без необходимости; на CI — кэшировать `Derived Data`/зависимости между запусками, если это поддерживает используемая система.
