---
title: "Как реализовать таймаут для await-выражения (withTimeout) и какие есть нюансы с отменой?"
category: concurrency
order: 119
---

Проблема: многие `async`-функции не имеют встроенного таймаута. Их выполнение может продолжаться бесконечно — например, если сервер не отвечает из-за сетевой ошибки, или из-за зависшего бага.

Решение — обернуть вызов в собственную функцию `withTimeout`, которая запускает основную операцию и таймер параллельно в `TaskGroup` и берёт результат того, кто finished первым:

```swift
enum TimeoutError: Error {
    case timedOut
}

func withTimeout<T>(
    seconds: Double,
    operation: @escaping @Sendable () async throws -> T
) async throws -> T {
    try await withThrowingTaskGroup(of: T.self) { group in
        group.addTask {
            return try await operation()
        }

        group.addTask {
            try await Task.sleep(nanoseconds: UInt64(seconds * 1_000_000_000))
            throw TimeoutError.timedOut
        }

        let result = try await group.next()!
        group.cancelAll()
        return result
    }
}
```

Как это работает:

- создаются две параллельные задачи: основная операция и таймер;
- кто быстрее — тот и выигрывает: `group.next()` возвращает результат первой завершившейся задачи;
- вторая (проигравшая) задача отменяется через `group.cancelAll()`, чтобы не работать впустую.

Нюансы с отменой:

- отмена в `withTimeout` требует, чтобы внутренняя операция **умела реагировать** на `Task.isCancelled` — если она не проверяет отмену, `group.cancelAll()` лишь выставит флаг, но реально работа не остановится;
- если внутренняя операция «зависла» внутри `await`, не реагирующего на отмену, `withTimeout` **не вернёт управление по таймауту**: `withThrowingTaskGroup` не завершается, пока не завершатся все дочерние задачи, даже после `cancelAll()`. Ошибка `TimeoutError.timedOut` будет выброшена только после того, как операция сама закончится; чтобы таймаут реально работал, операция должна поддерживать отмену (например, через `withTaskCancellationHandler`).

Использовать с осторожностью:

- для сетевых операций лучше сначала попробовать `URLSessionConfiguration.timeoutIntervalForRequest`, если он подходит по семантике — это нативный таймаут запроса без лишней обёртки;
- не оборачивать каждый `await` в таймаут «на всякий случай» — это дорого (лишняя задача и Task group на каждый вызов);
- использовать `withTimeout` для внешних вызовов, которые вы не контролируете (сторонние SDK, I/O), где встроенного таймаута нет и разработчик не может исправить саму зависимую операцию.
