---
title: "Что такое actor hop и как минимизировать overhead актор-актор сообщений?"
category: concurrency
order: 118
---

**Actor hop** — переключение исполнения из одного актора в другой. Происходит, когда:

- вы вызываете метод одного `actor` из контекста другого `actor`;
- или из контекста без актора (например, `Task.detached`) вызываете метод актора.

Каждое такое переключение — это не бесплатная операция, а:

- **контекстный переход** — actor scheduler ставит задачу в свою очередь;
- **приостановка** текущей задачи (`await`);
- **планирование** на другом actor executor.

```swift
actor FirstActor {
    let second = SecondActor()

    func doSomething() async {
        await second.work() // ← actor hop
    }
}

actor SecondActor {
    func work() async {
        print("Doing work")
    }
}
```

Здесь `FirstActor` делает actor hop к `SecondActor`.

Почему это важно:

- каждый hop — это потенциальный suspend-resume, даже если сам код короткий;
- это дороже обычного вызова функции: нужны приостановка и возобновление задачи, а не простой переход по адресу;
- многочисленные actor hop'ы внутри горячего пути (например, при обновлениях scroll-view, ML-инференсе, в графе зависимостей) приводят к заметному замедлению.

Как оптимизировать:

- **группировать вызовы одного актора** в один метод вместо нескольких отдельных `await`:

```swift
await secondActor.doMultipleThings() // лучше, чем 3 отдельных await
```

- **передавать данные, а не заставлять акторов запрашивать их друг у друга**:

```swift
await dataProcessor.process(data) // передали данные, а не контекст для запроса
```

- **избегать каскадных hop'ов**, когда один актор внутри своего метода вызывает другой, а тот — третий:

```swift
await actorA.callActorB { await actorC.work() } // ❌ тройной hop
```

**Advanced.** Для performance-critical кода используют `nonisolated`-методы внутри актора:

```swift
actor Processor {
    nonisolated func staticMethod() -> Int {
        42
    }
}
```

Такие методы не делают hop (не переключают исполнение на actor executor), но и не имеют доступа к изолированному состоянию (`self`) — подходят только для утилитных функций и констант, не зависящих от состояния актора.
