---
title: "Что такое @ViewBuilder? Какие проблемы он может привнести?"
category: swiftui
order: 52
---

`@ViewBuilder` — **result builder** (атрибут `@resultBuilder`), который позволяет писать список view подряд в декларативном блоке (как в `body`) и автоматически собирает их в единую составную view, а не требует явного массива или ручной обёртки.

```swift
@ViewBuilder
func content(isLoggedIn: Bool) -> some View {
    if isLoggedIn {
        ProfileView()
    } else {
        LoginView()
    }
}
```

Компилятор превращает такой блок в вызовы статических методов `ViewBuilder` (`buildBlock`, `buildEither(first:)`/`buildEither(second:)` для `if/else`, `buildOptional` для `if` без `else`, и т. д.), которые заворачивают перечисленные view в скрытые типы вроде `TupleView` или `_ConditionalContent` — именно поэтому `body` можно писать без явного `return` и без ручного построения массива.

Проблемы, которые он может привнести:

- **Ограничение на 10 элементов** в одном блоке — историческое ограничение старых SDK, где `buildBlock` был перегружен для фиксированного числа аргументов; превышение приводило к ошибке компиляции, и часть view приходилось группировать через `Group` или выносить в подвью. В современных SDK `buildBlock` вариативный (parameter packs), и лимита нет.
- **Каждая ветка меняет фактический тип возвращаемого значения** — `if/else` превращается в `_ConditionalContent<TrueView, FalseView>`, что раздувает тип и может замедлять компиляцию сложных `body`, а также усложняет чтение сообщений об ошибках типов.
- **Только выражения, возвращающие View** — внутри `@ViewBuilder`-блока нельзя писать произвольный императивный код (циклы `for` без `ForEach`, `print`, присваивания) — компилятор об этом сообщит, но новичков это часто удивляет.
- **Неявные преобразования усложняют отладку** — не всегда очевидно, во что конкретно резолвится тип `some View` при вложенных условиях, что затрудняет явную типизацию, если она вдруг понадобилась (например, для протокола с ассоциированным типом).
