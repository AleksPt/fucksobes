---
title: "Есть ViewController и замыкание. Мы закрыли ViewController, на него нет сильных внешних ссылок, но память не очистилась. Почему?"
category: memory
order: 73
---

Потому что сильная ссылка на `ViewController` может держаться не *снаружи*, а *внутри* него самого — через замыкание.

Типичная причина — **цикл сильных ссылок** между `self` и escaping-замыканием:

- `ViewController` где-то хранит замыкание (в свойстве, в сетевом запросе, в таймере, в обработчике уведомлений) — то есть сам держит сильную ссылку на замыкание;
- это замыкание захватывает `self` без `[weak self]` — то есть держит сильную ссылку на контроллер.

Получается цикл: `VC → closure → VC`. Даже когда все внешние ссылки (навигационный стек, презентующий контроллер) исчезли, объекты внутри цикла продолжают держать друг друга живыми, и ARC не может их освободить — `deinit` не вызывается, память не возвращается.

```swift
final class ProfileViewController: UIViewController {
    var onUpdate: (() -> Void)?

    override func viewDidLoad() {
        super.viewDidLoad()
        // Сильный захват self создаёт цикл, если onUpdate хранится дольше жизни VC
        onUpdate = {
            self.reload()
        }
    }
}
```

Похожая ситуация возникает и без явного свойства-замыкания:

- долгоживущий **таймер** (`Timer.scheduledTimer`) или **observer** (`NotificationCenter`), который держит замыкание с сильным `self` и не был инвалидирован/отписан;
- сетевой запрос с `escaping`-замыканием, который ViewController не отменил при закрытии, а сама `URLSession` держит и запрос, и его completion-замыкание.

Исправление — захватывать `self` слабо там, где замыкание может пережить сам объект:

```swift
onUpdate = { [weak self] in
    self?.reload()
}
```

Найти такие утечки помогают **Memory Graph Debugger** в Xcode (виден цикл ссылок между VC и замыканием) и **Instruments → Leaks**.
